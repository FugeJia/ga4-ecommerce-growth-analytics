# 项目讲述与局限

## 60 秒讲述

我做的是一个可以从头重跑的数据分析工程，而不只是截图。它围绕 GA4 电商事件结构，从 BigQuery 只抽取所需字段，再用 DuckDB 做有序会话漏斗、first_visit cohort 留存、交易去重和 RFM，最后用 Streamlit 展示。

我重点处理了三个容易误算的问题：session_id 必须与用户键组合，漏斗必须满足事件先后顺序，留存必须排除尚未观察满 D7/D30 的用户。每次输入和构建都有数据模式与 hash，合成演示不会被包装成真实经营结果。

目前没有 Google Cloud 项目，所以交付版本完成了可运行合成演示、云端抽取实现与自动化测试；还没有真实数据结论。实验模块是独立方法工具，没有从非随机事件数据编造真实 A/B 效果。

## 能解释的取舍

- 为什么不用“访问→注册→激活→首单”？公开样例不能保证 sign_up 和引导事件存在；购买链路更贴合可验证电商事件，注册/引导保留为未来事件设计。
- 为什么严格排除同时间戳？历史样例缺少足够可靠的 batch 顺序；保守不推断可避免伪造路径，代价是低估部分漏斗转化。
- 为什么不用所有用户首个事件算新增？观察窗口之前可能已经访问；first_visit 证据更明确，但仍受匿名 ID 重置和混淆限制。
- 为什么保留交易冲突门禁？相同 transaction_id 跨用户会污染 RFM；应先检查，不把歧义悄悄聚合。
- 为什么不用 p<.05 自动上线？还需要随机化与 SRM、结果成熟、实际提升方向、置信区间和护栏。
- 为什么没有真实业务提升数字？工程指标与业务成效需要不同证据；没有执行或实验就不写成事实。
